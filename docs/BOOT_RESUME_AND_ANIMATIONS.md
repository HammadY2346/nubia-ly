# Boot animations and background resume

## Implemented: background resume

The app's signature-protected BootResumeReceiver handles Android BOOT_COMPLETED and the guard's explicit RESUME_AFTER_UNLOCK broadcast. It checks NX809J / SDK 36, owner user 0, unlocked credential storage and existing enabled identity. It starts no Activity, foreground service or root process. A worker reads the guard/private preference latch, then the existing SystemUiGuardClient requests clock_resume. The fingerprint client nudges its independently scoped runtime; both hosts still fetch and validate their own authority. Concurrent broadcasts coalesce. Emergency stop, revoked/missing guard identity and startup-recovery limits remain authoritative. No call to allowEnabled, activate or enable_clock occurs during resume.

The guard service publishes only a previously saved root identity as before. It additionally performs at most 60 two-second checks for completed boot and RUNNING_UNLOCKED owner state. If ready, guardctl resume_app validates the current boot receipt against the durable root-owned identity and sends a fixed explicit broadcast to nubia-ly, including stopped packages. This wakes the app process in the background, without opening its dashboard. The Android boot broadcast is the normal first-unlock path, including later unlocks after this short guard fallback window; root nudges are not a permanent daemon. A user/OEM force-stop combined with delaying unlock beyond the guard window can prevent that fallback and needs phone validation. Module Action/removal revokes identity; resume_app cannot recreate it.

The prior clock broker read draft clock preferences during resume, unlike the already-frozen status-bar/surface configuration. Enable now atomically stores ClockSnapshot with the existing active status-bar identity. Subsequent drafts do not change resumed clock color/size/weight/seconds/italic/spacing/family/visibility. Older applied snapshots without active_clock use stock clock settings, preserving their separately saved applied surfaces. **Upgrade test: press Enable once to capture the new clock snapshot; later reboots require no Apply.** Invalid snapshots and mismatched identities fail to stock. No migration guesses which historic clock draft was last applied.

Guard version 0.1.15 (16), app 0.1.55-systemless-boot (56). This branch includes the pending PR #28 editor navigation cleanup; that change has not been merged independently.

## Systemless boot animations

App 0.1.55-systemless-boot (56), guard 0.1.15 (16). The owner supplied `system/bin/bootanimation`, `system/lib64/libbootanimation.so` and the generic stock ZIP. Library SHA-256 is `8a254699242729e1af694850415b60a8c98201fae8f3aec5c17ff188d2e12d55`; generic stock archive is `fde98dca1d1452e4c5f22f327ffd540af3a8e4f5f8ee1e225aa55e0f312457c5` with `1216 2688 25`, stored frames and two parts. Those owner files are inspection inputs and are not committed or redistributed.

The actual exported `findBootAnimationFile` was disassembled. It checks a readable `persist.sys.customanim.boot` path, fans mode, then `/system/media/<persist.vendor.custom.variant.id>/bootanimation.zip` before AOSP fallbacks. The library also implements the stored-ZIP requirement, trim metadata and dynamic-color shader. The loader pins this exact library and supports only the regular/carrier branch: variant is at most 32 ASCII letters/digits/underscore/hyphen; paths must be canonical regular files, and arbitrary readable custom paths/fans/userspace-reboot modes are blocked. When the carrier candidate is absent, it supports the generic fallback only with default theme/file properties and no competing APEX, OEM, product or dark archive. The owner confirmed GEN_NON_EEA has no carrier archive and only the generic system archive exists. Stage-time verified target is retained for early boot when persisted vendor properties have not loaded yet.

A compact Boot animations dashboard entry opens its own page, showing finite source-frame previews and five visual cards. Selection is a private app draft. Apply copies a pinned archive into one fixed app-private file; the root script reads only that fixed regular canonical file, bounds byte count, rechecks SHA-256 and deadline, and atomically stages a root-private payload and selection. No phone downloads, arbitrary ZIP imports, supplied paths, shell strings or automatic reboot. All five ZIPs are generated into assets by CI from immutable upstream URLs and verified hashes; previews use the original frames/proportions and default dynamic-color palette. They stop on page exit. The APK is larger because it contains the source archives.

### Systemless loader and recovery

The guard retains skip_mount and ships no system replacement tree. Its post-fs-data hook performs one explicit `mount -o bind,dev=KSU` from its root-private verified payload onto the resolved animation **file**, following KernelSU's documented source-tag convention. It does not require or install a general mounting metamodule. This direct bind still needs phone validation. There is no broader fallback, partition remount, property write, directory overlay, stock-file copy-back, init replacement, player restart or live unmount.

Stage records the current original file hash, scoped target and ownership. Boot validates those again, excludes an existing exact-file mount, clones the original SELinux file label onto our payload only, and verifies the resulting inode through `/proc/1/root` against our source inode. This proves visibility in PID 1's namespace rather than trusting the app/su namespace. If that proof fails, the selection is disarmed and reported as unverified. The original bytes are never written. Re-staging while our older inode remains bound preserves the recorded original baseline; future boot sees the new staged inode.

Before mounting, an attempt receipt records the boot UUID. A separate bounded service worker confirms only after sys.boot_completed=1 with a matching current mount receipt/inode; no app launch/unlock is required for this acknowledgement. An unconfirmed prior attempt disarms the next boot before mounting. A 120-second boot-completion timeout also disarms future boots without forcing reboot. A successful Android boot does not prove that the animation was visually rendered; the phone test is still required. A power loss before completion can conservatively trigger rollback.

Restore deletes only our selection/payload/attempt, leaving a current bind to expire naturally on reboot. Guard Action/uninstall also invoke this stop; app emergency stop requests root guard stop. Lock serialization prevents a successful Restore racing a stage commit; a busy/unsafe stop reports failure rather than claiming success. Clock-authority removal still runs if the boot stop fails. Locks from dead writers/prior boots have bounded, fixed-entry recovery. Symlink/non-root/writable state directories are refused. Fixed result codes distinguish staging, completed boot, mount failure and rollback. No claim of universal boot-loop recovery is made.

### Final validation / phone batch

Added host shell regression covers pinned ZIP staging, malformed input rejection, no live apply, unchanged original sentinels, default and JD_ID carrier paths, missing early vendor properties, existing-inode ownership while restaging, confirmed and unconfirmed boots, mount/namespace failure, explicit Restore, module disable, changed player, custom/fans exclusion, corrupted metadata removal, symlink and busy-stop fences. All mount operations in the host suite are emulated; no host system files are mounted or written. Root app contract tests cover fixed IDs, strict status parsing and rejection before root when archive identity fails. Existing background-resume/policy/guard tests remain.

Install the matching APK and guard ZIP, reboot, open Boot animations and verify Ready. Preview/select Rising, Apply on next boot, then reboot and observe. Check module state afterward: selected and mounted should match. Test Restore + reboot, then apply another style and test guard Action + reboot. Source archives may letterbox because their original proportions differ. Test an additional reboot for persistence and first-unlock restoration of enabled System UI features. Enable once in this upgrade to establish ClockSnapshot; later boots restore it without Apply. A different later draft must stay unapplied. Check long first-unlock delay as well.

The incomplete-boot rollback is host-tested but not yet demonstrated on the phone; do not deliberately induce a boot failure as the first test. If a mount is blocked, stock should remain active and the UI reports that result. Keep root-manager module disable/recovery access available for device testing. Nothing is merged until the user approves.
