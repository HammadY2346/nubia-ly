# Unlock resume and systemless boot-animation preparation

## Implemented: background resume

The app's signature-protected BootResumeReceiver handles Android BOOT_COMPLETED and the guard's explicit RESUME_AFTER_UNLOCK broadcast. It checks NX809J / SDK 36, owner user 0, unlocked credential storage and existing enabled identity. It starts no Activity, foreground service or root process. A worker reads the guard/private preference latch, then the existing SystemUiGuardClient requests clock_resume. The fingerprint client nudges its independently scoped runtime; both hosts still fetch and validate their own authority. Concurrent broadcasts coalesce. Emergency stop, revoked/missing guard identity and startup-recovery limits remain authoritative. No call to allowEnabled, activate or enable_clock occurs during resume.

The guard service publishes only a previously saved root identity as before. It additionally performs at most 60 two-second checks for completed boot and RUNNING_UNLOCKED owner state. If ready, guardctl resume_app validates the current boot receipt against the durable root-owned identity and sends a fixed explicit broadcast to nubia-ly, including stopped packages. This wakes the app process in the background, without opening its dashboard. The Android boot broadcast is the normal first-unlock path, including later unlocks after this short guard fallback window; root nudges are not a permanent daemon. A user/OEM force-stop combined with delaying unlock beyond the guard window can prevent that fallback and needs phone validation. Module Action/removal revokes identity; resume_app cannot recreate it.

The prior clock broker read draft clock preferences during resume, unlike the already-frozen status-bar/surface configuration. Enable now atomically stores ClockSnapshot with the existing active status-bar identity. Subsequent drafts do not change resumed clock color/size/weight/seconds/italic/spacing/family/visibility. Older applied snapshots without active_clock use stock clock settings, preserving their separately saved applied surfaces. **Upgrade test: press Enable once to capture the new clock snapshot; later reboots require no Apply.** Invalid snapshots and mismatched identities fail to stock. No migration guesses which historic clock draft was last applied.

Guard version 0.1.13 (14), app 0.1.54-unlock-resume (55). This branch includes the pending PR #28 editor navigation cleanup; that change has not been merged independently.

## Prepared, not activated: boot animations

Five actual Rising candidates were downloaded and inspected, with their source commit and full byte hashes pinned in third_party/rising-bootanimations/catalog.json. Their stored ZIPs contain only animation frames, descriptor/trim metadata and directories. The candidates differ in dimensions: Rising 1080x2400, Cyberpunk 1080x1920 (864-wide image frames), Valorant 1080x840, Google 960x2142, Google Monet 1080x2338. Google Monet uses the AOSP dynamic_colors extension and needs player verification. Archive bytes are not yet bundled in the app or module.

scripts/inspect-bootanimations.py can verify an explicitly named cache offline or download only those pinned upstream files with --download. It bounds archives, members, sizes and frame counts; checks identity, stored compression, duplicate/traversal/symlink/encrypted entries and descriptor parts. It performs no extraction, root command, mount or activation.

**Blocked on device evidence:** the REDMAGIC boot-animation player's selected filename, path precedence, ZIP/trim/dynamic-color support and installed root manager/mount provider have not been confirmed. The requested read-only Termux output is still needed. Do not choose /product/media or any other target from generic AOSP conventions. If strings output is insufficient, inspect the owner's actual bootanimation binary and current stock animation ZIP next.

The future contract is systemless only: stage a known verified ZIP in our root-private/module namespace; expose one confirmed stock animation file through the root manager's overlay; never remount/write system partitions, change bootloader splash or replace stock files. The guard will need an early boot trial/recovery path: incomplete prior boot disarms the next overlay, success is acknowledged independently of app launch, Restore/Action/removal disarms future boots, and any already-mounted override remains until reboot. This is a design constraint, not implemented recovery behavior. Do not promise boot-loop protection before testing it.

The current module still contains skip_mount and **no boot-animation overlay or early-boot mounting code**. Installing this revision does not change the boot animation. Boot animations and their guard support remain outstanding until the device check arrives.

## Validation and phone test

Host tests cover receiver action/device/user/unlock/authority gates, concurrent request coalescing and async completion; guard current-boot/identity matching, disabled/stopped state, no authority minting, unlock condition and bounded polling; frozen clock state, invalid snapshots and draft/applied separation. Existing guard and recovery tests remain. Android compilation/tests and signed packaging use GitHub Actions only.

Install app and updated guard ZIP, reboot, Enable the desired appearance once for this upgrade, then edit a distinctly different draft without Enable. Reboot again and unlock without opening nubia-ly. The enabled appearance should return and the draft should remain unapplied. Test a delayed first unlock, startup recovery, guard Action, and a reboot with the guard disabled. Confirm no dashboard opens. Restore stock remains available. Do not test boot-animation activation: it is not present yet.
